    01 El reto

    Tres preguntas,un mapa.

    Una empresa de transporte intermunicipal necesita un sistema de software para gestionar sus buses y parqueaderos dentro de los límites de Cundinamarca, Colombia. Diseñamos un sistema de información geográfica sobre PostGIS y el mapa dinámico de OpenStreetMap, documentado con el modelo de vistas arquitectónicas 4+1, y lo entregamos como sistema web y como app móvil en Cordova.

    a

    Disponibilidad de cupos

    “¿Cuántos cupos libres hay ahora en cada terminal?”

    Cada llegada abre un parking_stay; cada salida lo cierra. v_parking_availability compara las estadías abiertas con la capacidad máxima de cada parqueadero, y un trigger bloquea el parqueadero para que nunca se sobrepase.

    b

    Ubicación de buses

    “¿Dónde está el bus CB-127?”

    No se necesita GPS: el bus se ubica en el parqueadero de su estadía abierta. Mientras un viaje está en ruta, PostGIS estima su posición sobre el trayecto con ST_LineInterpolatePoint según el tiempo transcurrido.

    c

    Puestos por bus

    “¿Quedan puestos en el de las 13:05 a Ubaté?”

    Cada ticket guarda un número de puesto de un viaje. Puestos disponibles = capacidad del bus − tiquetes vendidos. La base de datos rechaza puestos duplicados, puestos inexistentes y ventas después de la salida.

    03 Arquitectura

    El modelode vistas 4+1.

    El modelo de Kruchten describe el sistema desde el punto de vista de cada interesado. Cuatro vistas — lógica, de procesos, de desarrollo y física — se integran y validan con una quinta: los escenarios (casos de uso).

    Escenarios

    Interesados · todos — valida las otras cuatro vistas

    Casos de uso derivados del taller. Cada uno se rastrea en las demás vistas: p. ej. Registrar llegada se vuelve la clase ParkingStay (lógica), la secuencia de llegada (procesos), api_register_arrival (desarrollo) y una llamada del celular a Supabase (física).

    • Administrador del parqueadero registra llegadas, salidas e información de viajes de su terminal.
    • Despachador sigue la disponibilidad, los buses en ruta y los horarios de conductores.
    • Pasajero / taquillero encuentra la terminal más cercana y consulta o vende puestos.
    • Administrador del sistema gestiona terminales, siempre dentro de Cundinamarca.

    Vista lógica

    Interesados · usuarios finales, analistas — funcionalidad

    El modelo de dominio. Los objetos espaciales (ServiceArea, ParkingLot) llevan geometrías PostGIS; toda la operación cuelga del Trip (la “información del bus”) y del ParkingStay (lo que registra el administrador).

    • ParkingStay = una llegada + una salida → el tiempo real de permanencia.
    • Trip = origen, destino, salida, llegada y permanencia planeada.
    • Ticket = un puesto de un viaje → disponibilidad de puestos.
    • DriverShift = horario de servicio del conductor, con base en una terminal.

    Vista de procesos

    Interesados · integradores — concurrencia, desempeño

    Comportamiento en ejecución del escenario más crítico: registrar la llegada de un bus. Toda la operación es una única transacción de PostgreSQL ejecutada por una función RPC.

    • Concurrencia: el trigger de capacidad bloquea la fila de parking_lot (FOR UPDATE), así dos administradores no pueden ocupar el último cupo al mismo tiempo.
    • Los errores se lanzan en SQL y regresan como mensajes legibles.
    • El mapa consulta api_overview() cada 30 s — una sola petición trae parqueaderos, buses y estadísticas.
    • Los buses en ruta se reinterpolan en el cliente cada 15 s.

    Vista de desarrollo

    Interesados · programadores — organización del código

    Capas y los archivos que las implementan. Las reglas de negocio viven en la base de datos, así el sistema web, la app Cordova y cualquier cliente futuro obedecen exactamente las mismas reglas.

    • app/ se comparte tal cual entre la web y la app móvil (npm run sync).
    • api.js es el único módulo que habla con la red.
    • El SQL se versiona en orden: esquema → reglas → vistas → datos → API.

    Vista física

    Interesados · ingenieros de sistemas — despliegue, topología

    Dónde corre cada pieza. Los clientes son livianos: dibujan el mapa OSM y llaman a la API de Supabase por HTTPS. El único servidor es el proyecto administrado de Supabase, desplegado en la región us-east-1 (Virginia, EE. UU.).

    • Celulares: WebView de Cordova + GPS del dispositivo (plugin de geolocalización).
    • Supabase: API PostgREST delante de PostgreSQL 17 + PostGIS 3.
    • OpenStreetMap: mosaicos raster y geocodificación con Nominatim.
    • Sin servidor de aplicaciones que mantener.
    04 Base de datos

    PostGIS haceel trabajo.

    Solo dentro de Cundinamarca

    Cada terminal se valida contra los polígonos del departamento importados de OpenStreetMap.

    CREATE FUNCTION fn_in_service_area(p geometry) RETURNS boolean AS $$
  SELECT EXISTS (SELECT 1 FROM service_area sa
                 WHERE ST_Covers(sa.geom, p));
$$;
-- BEFORE INSERT OR UPDATE OF geom ON parking_lot
-- → RAISE 'La ubicación está fuera de Cundinamarca'
    Nunca sobre la capacidad

    La fila del parqueadero se bloquea antes de contar, así las llegadas concurrentes se serializan.

    SELECT capacity INTO v_capacity FROM parking_lot
 WHERE id = NEW.parking_lot_id FOR UPDATE;
SELECT count(*) INTO v_occupied FROM parking_stay
 WHERE parking_lot_id = NEW.parking_lot_id
   AND departed_at IS NULL;
IF v_occupied >= v_capacity THEN RAISE EXCEPTION 'El parqueadero % está lleno'…
    Terminal más cercana (KNN)

    Dirección geocodificada → terminales más cercanas usando el índice GiST y el operador de distancia <->.

    SELECT code, municipality, available,
       ST_DistanceSphere(pl.geom, q.g) / 1000 AS km
  FROM parking_lot pl JOIN v_parking_availability USING (id)
 ORDER BY pl.geom <-> ST_SetSRID(ST_MakePoint(lng, lat), 4326)
 LIMIT 3;
    Posición estimada en ruta

    No se requiere rastreo en tiempo real; mientras está en ruta, el bus se ubica sobre su trayecto según el tiempo transcurrido.

    ST_LineInterpolatePoint(
  ST_MakeLine(origin.geom, destination.geom),
  LEAST(1, GREATEST(0,
    extract(epoch FROM now() - t.actual_departure) /
    extract(epoch FROM t.scheduled_arrival - t.scheduled_departure))))
    05 El sistema

    En vivo, sobreOpenStreetMap.

    Este es el sistema de información real funcionando contra la base de datos en Supabase — no es una maqueta. Abra una terminal, registre una salida, venda un puesto o busque una dirección: cada acción pasa por las reglas de PostGIS de arriba.

    Terminales

    Cupos libres, buses parqueados, permanencia, próximas salidas, llegadas y turnos de conductores por terminal.

    En vivo

    Un bus 3D recorre la vía real (OSRM) según la hora; síguelo con la cámara o acelera el reloj ×30 a ×600.

    Registrar

    Llegadas, salidas y nuevos viajes con origen, destino, horas y permanencia.

    Puestos

    Mapa de puestos por bus y viaje; venda un puesto y vea cómo se actualiza la disponibilidad.

    06 App móvil

    En el bolsillode cada admin.

    La app móvil está hecha con Apache Cordova. Empaqueta exactamente el mismo código del sistema web, cambia a un panel inferior deslizable en pantallas pequeñas y usa el GPS del dispositivo para encontrar la terminal más cercana.

    1. Mismo código. npm run sync copia app/ en mobile/www e inyecta cordova.js.
    2. GPS nativo. cordova-plugin-geolocation alimenta la consulta KNN de “terminal más cercana”.
    3. Hecha para el patio. Botones grandes, navegación inferior a una mano, funciona en Android 7+.
    mobile/
    $ npm install
$ npm run sync              # app/ → www/
$ npx cordova platform add android
$ npx cordova run android   # o: npm run browser

    Pegue la URL del proyecto y la llave pública en app/js/config.js.

    03

    Servir

    Sirva la carpeta (p. ej. npx serve .) y abra esta página o app/.

    Móvil
